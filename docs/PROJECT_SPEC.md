# سند نیازمندی و برنامهٔ ساخت سامانهٔ کلینیک توانبخشی

**نام موقت:** Rehab Clinic Management  
**نسخه:** 1.1  
**وضعیت:** آماده برای Claude Code Plan Mode  
**زبان محصول:** فارسی و راست‌به‌چپ  
**محصول نسخهٔ اول:** وب‌سایت عمومی و پنل داخلی در Next.js + API و منطق دامنه در NestJS

---

## 1. هدف سند

این فایل منبع اصلی نیازمندی‌های نسخهٔ اول پروژه است. Claude Code باید قبل از هر برنامه‌ریزی یا کدنویسی آن را کامل بخواند.

در اولین اجرا، Claude Code فقط باید:

1. دامنه و قواعد کسب‌وکار را تحلیل کند.
2. ابهام‌ها و تصمیم‌های باز را مشخص کند.
3. معماری، مدل داده، تست‌ها و مراحل اجرا را پیشنهاد دهد.
4. هیچ فایل یا کدی ایجاد یا ویرایش نکند.
5. پس از تأیید انسان، فقط یک مرحلهٔ کوچک و مشخص را اجرا کند.

---

## 2. مسئلهٔ اصلی

کلینیک در ثبت و محاسبهٔ اطلاعات روزمره مشکل دارد:

- نوبت‌ها و جلسات در چند محل یا به‌صورت دستی ثبت می‌شوند.
- خانواده ممکن است چند جلسه دریافت کند و پرداخت را عقب بیندازد.
- منشی هنگام شمارش جلسات یا محاسبهٔ بدهی اشتباه می‌کند.
- پرداخت کامل، ناقص و وعدهٔ پرداخت ساختار مشخصی ندارد.
- معلوم نیست هر خانواده دقیقاً چند جلسه، چه مبلغ بدهی و چه میزان پرداخت داشته است.
- تغییر تعرفه یا اصلاح دستی ممکن است حساب گذشته را خراب کند.
- محاسبهٔ سهم درمانگران دستی و مستعد خطاست.
- مدیر نمای یکپارچه‌ای از نوبت، جلسه، پرداخت و مطالبات ندارد.
- وب‌سایت فعلی برای معرفی حرفه‌ای و جذب درخواست کافی نیست.

مشکل فوری نسخهٔ اول، پرداخت آنلاین نیست؛ مشکل فوری، **ثبت قابل اتکا و محاسبهٔ خودکار و قابل حسابرسی** است.

## 3. تصمیم محصول

نسخهٔ اول دو بخش متصل دارد:

### 3.1 وب‌سایت عمومی

برای معرفی کلینیک، خدمات، تیم، مقالات، نظرات، آدرس و دریافت درخواست تماس یا نوبت.

### 3.2 پنل داخلی

برای استفادهٔ مدیر و منشی جهت:

- ثبت خانواده و کودک
- ثبت و مدیریت نوبت
- ثبت وضعیت واقعی جلسه
- ایجاد خودکار هزینهٔ جلسهٔ انجام‌شده
- ثبت پرداخت کامل یا ناقص
- محاسبهٔ مانده‌حساب خانواده
- ثبت وعدهٔ پرداخت و پیگیری سررسید
- مشاهدهٔ بدهکاران
- مدیریت درمانگران، خدمات، اتاق‌ها و تعرفه‌ها
- گزارش‌گیری پایه

### 3.3 اصل کلیدی

> ورود اطلاعات توسط منشی دستی است، اما شمارش و تمام محاسبات مالی باید توسط سیستم انجام شود.

منشی نباید تعداد جلسات، مجموع هزینه، مجموع پرداخت یا مانده را با ماشین‌حساب محاسبه کند.

### 3.4 تصمیم معماری محصول

نسخهٔ اول با دو Application در یک Monorepo ساخته می‌شود:

- **Next.js:** وب‌سایت عمومی، پنل داخلی و لایهٔ محدود Backend for Frontend.
- **NestJS:** API اصلی، احراز هویت و مجوز نهایی، منطق کسب‌وکار، تراکنش‌ها، Audit و دسترسی انحصاری به PostgreSQL.

این ساختار Microservice محسوب نمی‌شود. NestJS یک **Modular Monolith** است و Next.js لایهٔ Presentation/BFF همان محصول است.

قانون مرزی:

> هیچ منطق مالی، قانون نوبت، محاسبهٔ مانده، مجوز نهایی یا دسترسی مستقیم دیتابیس در Next.js پیاده‌سازی نمی‌شود.

Next.js می‌تواند داده را برای UI ترکیب یا کوچک کند، Session مرورگر را مدیریت کند و درخواست Client Component را به NestJS منتقل کند؛ اما NestJS همیشه منبع حقیقت قواعد دامنه و امنیت است.

## 7. واژه‌نامه

- **خانواده:** واحد اصلی حساب مالی؛ می‌تواند چند کودک داشته باشد.
- **کودک:** دریافت‌کنندهٔ جلسه؛ به یک خانواده متصل است.
- **نوبت:** برنامهٔ زمانی برای کودک، درمانگر، خدمت و اتاق.
- **جلسهٔ انجام‌شده:** نوبتی که واقعاً برگزار شده است.
- **هزینه (Charge):** بدهی مستقل ایجادشده برای جلسه یا اصلاح مالی.
- **پرداخت:** وجه ثبت‌شده از طرف خانواده.
- **تخصیص پرداخت:** ارتباط پرداخت با یک یا چند هزینه.
- **مانده:** مجموع هزینه‌های معتبر منهای پرداخت‌ها و اعتبارها.
- **وعدهٔ پرداخت:** تعهد خانواده برای تاریخ آینده؛ خودش پرداخت نیست.
- **ابطال:** بی‌اثرکردن رکورد با حفظ کاربر، زمان و دلیل؛ نه حذف.

### 9.5 قواعد تعرفه

- تغییر تعرفه نباید مبلغ جلسهٔ گذشته را عوض کند.
- هر نوبت یک Snapshot قیمت داشته باشد.
- قیمت تا پیش از انجام جلسه با دسترسی مجاز قابل اصلاح است.
- پس از انجام، تغییر با Adjustment ثبت شود.
- تعرفهٔ خاص خانواده بر تعرفهٔ عمومی اولویت دارد.
- نبود تعرفه باید هشدار واضح ایجاد کند.
- مبلغ با Integer ذخیره شود، نه Float.

### 11.2 ثبت نوبت

- درمانگر
- اتاق
- تاریخ و ساعت شروع
- مدت و ساعت پایان محاسبه‌شده
- قیمت پیشنهادی و Snapshot
- وضعیت
- یادداشت
- سری تکرارشونده، اختیاری

### 11.3 نوبت تکرارشونده

- تکرار هفتگی
- چند روز در هفته
- تعداد جلسه یا تاریخ پایان
- پیش‌نمایش پیش از ایجاد
- هشدار تداخل
- ویرایش یک نوبت
- ویرایش این نوبت و بعدی‌ها
- لغو یک نوبت یا باقی سری

### 11.4 وضعیت‌ها

- `SCHEDULED`
- `COMPLETED`
- `CANCELLED_BY_FAMILY`
- `CANCELLED_BY_CLINIC`
- `NO_SHOW`
- `RESCHEDULED`
- `VOIDED`

### 11.5 تداخل

سیستم باید از این موارد جلوگیری کند یا هشدار کنترل‌شده بدهد:

- دو نوبت هم‌زمان برای درمانگر
- دو نوبت هم‌زمان برای اتاق
- دو نوبت هم‌زمان برای کودک
- نوبت خارج از ساعت حضور
- استفاده از اتاق یا درمانگر غیرفعال

### 11.6 قواعد مالی نوبت

- فقط `COMPLETED` هزینهٔ اصلی ایجاد می‌کند.
- هر نوبت حداکثر یک هزینهٔ اصلی دارد.
- عملیات باید Idempotent باشد؛ Refresh یا ارسال تکراری هزینهٔ دوم نسازد.
- لغو عادی هزینه ندارد.
- سیاست هزینهٔ عدم حضور هنوز تصمیم‌گیری نشده است.
- پیش‌فرض MVP: `NO_SHOW` هزینه ایجاد نمی‌کند.
- برگشت از `COMPLETED` فقط با دسترسی و دلیل مجاز است.
- در برگشت، هزینه حذف نشود؛ باطل یا معکوس شود.

## 25. سناریوهای پذیرش حیاتی

### سناریو 1: پرداخت دیرهنگام

سه جلسهٔ 1,000,000 ایجاد می‌شود؛ بدهی 3,000,000 است. خانواده 1,000,000 می‌پردازد؛ مانده 2,000,000 است. وعدهٔ 2,000,000 ثبت می‌شود ولی مانده تغییر نمی‌کند. در سررسید، وعده دیده می‌شود. پس از پرداخت دوم، مانده صفر و وعده انجام‌شده است.

### سناریو 2: دو کودک

یک خانواده دو کودک و مجموع پنج جلسه دارد. حساب مجموع را نشان می‌دهد و جزئیات هر کودک جداست. یک پرداخت می‌تواند بدهی هر دو را پوشش دهد.

### سناریو 3: لغو

نوبت لغوشده هزینه نمی‌سازد و در گزارش لغو دیده می‌شود.

### سناریو 4: جلوگیری از هزینهٔ تکراری

تغییر وضعیت به انجام‌شده، Refresh یا ارسال مجدد نباید Charge دوم ایجاد کند.

### سناریو 5: تعرفه

افزایش تعرفه امروز، مبلغ جلسهٔ گذشته را تغییر نمی‌دهد و برای نوبت جدید پیشنهاد می‌شود.

### سناریو 6: ابطال پرداخت

مدیر با دلیل پرداخت را باطل می‌کند؛ مانده برمی‌گردد و رکورد در تاریخچه باقی می‌ماند.

### سناریو 7: تداخل

دو نوبت هم‌زمان برای درمانگر، اتاق یا کودک مسدود یا نیازمند Override مجاز است.

### سناریو 8: نوبت تکرارشونده

ده نوبت ایجاد می‌شود. تغییر یکی، بقیه را بدون انتخاب صریح تغییر نمی‌دهد.

### سناریو 9: اصلاح مالی

مبلغ اشتباه با Adjustment اصلاح می‌شود؛ مقدار قبلی، جدید و دلیل حفظ می‌شود.

### سناریو 10: درخواست سایت

فرم در صندوق جدید ظاهر می‌شود؛ تماس ثبت و در صورت مراجعه به خانواده متصل می‌شود.

## 27. معماری پیشنهادی

### 27.1 رویکرد کلان

**Next.js Frontend/BFF + NestJS Modular Monolith + PostgreSQL**

دلایل انتخاب:

- توسعه‌دهنده با NestJS و Next.js آشناست؛ هزینهٔ یادگیری و خطای اجرایی کمتر می‌شود.
- Next.js برای سایت عمومی، صفحات Server-rendered، Metadata، Sitemap و تجربهٔ مناسب SEO کاربرد دارد.
- NestJS مرز روشن برای DTO، Validation، Guard، تراکنش، Audit و منطق مالی ایجاد می‌کند.
- پنل و سایت یک تجربهٔ یکپارچه دارند، اما منطق حساس مالی از UI جدا می‌ماند.
- TypeScript در دو سمت، کار با قرارداد API و Claude Code را ساده‌تر می‌کند.
- Backend همچنان یک Modular Monolith و دارای یک دیتابیس است؛ پیچیدگی Microservice وارد MVP نمی‌شود.

### 27.2 Stack تأییدشده برای Plan Mode

- Language: TypeScript با Strict Mode
- Monorepo: pnpm workspaces؛ استفاده از Turborepo در صورت توجیه در Plan
- Web/BFF: Next.js App Router
- API: NestJS REST API
- Database: PostgreSQL
- API Contract: OpenAPI تولیدشده از NestJS + TypeScript Client تولیدشده برای Next.js
- Validation نهایی: NestJS DTO و ValidationPipe
- Styling: Tailwind CSS یا راهکار ساده و کنترل‌شده
- API Test: Jest + Supertest یا معادل استاندارد NestJS
- End-to-End Test: Playwright برای مسیرهای حیاتی
- Development: Docker Compose
- Production: دو Process/Container برای `web` و `api` + PostgreSQL
- Reverse Proxy/Ingress: یک Domain عمومی؛ API داخلی تا حد ممکن مستقیماً در اینترنت منتشر نشود
- CI: Typecheck، Lint، Test، Build و Migration Check

نسخهٔ Packageها باید در زمان ایجاد پروژه از مستندات رسمی و نسخه‌های پایدار سازگار انتخاب و سپس Lock شوند. Claude Code نباید بر اساس حافظهٔ قدیمی شمارهٔ نسخه حدس بزند.

### 27.3 ساختار Monorepo پیشنهادی

```text
apps/
  web/                    # Next.js public website, admin panel, selective BFF
  api/                    # NestJS modular monolith and database owner
packages/
  api-client/             # generated TypeScript client from Nest OpenAPI
  config/                 # shared lint/tsconfig conventions, no secrets
  ui/                     # optional shared UI components; create only when justified
docs/
  PROJECT_SPEC.md
  CLAUDE_CODE_WORKFLOW.md
CLAUDE.md
```

از ایجاد Packageهای متعدد پیش از نیاز واقعی خودداری شود.

### 27.4 مسئولیت NestJS

NestJS تنها مالک موارد زیر است:

- اتصال و Migration دیتابیس
- Entity/Model و Repository
- قواعد خانواده و کودک
- برنامهٔ درمانگر و تداخل نوبت
- State Transition نوبت
- ایجاد Idempotent هزینه از جلسهٔ انجام‌شده
- Ledger، Payment، Allocation، Credit و Balance
- وعدهٔ پرداخت
- تخفیف، Adjustment و Void
- تسویهٔ درمانگر
- RBAC و مجوز نهایی هر عملیات
- Audit Log
- Validation نهایی ورودی
- گزارش‌های مالی و عملیاتی منبع
- تولید OpenAPI

فقط `apps/api` اجازهٔ دسترسی مستقیم به PostgreSQL دارد.

### 27.5 مسئولیت Next.js

Next.js مسئول موارد زیر است:

- وب‌سایت عمومی و SEO
- پنل فارسی و RTL
- Server Components و Client Components
- مدیریت Session مرورگر و Cookie امن بر اساس طرح Auth تأییدشده
- فرم‌ها، UX، نمایش Validation Error و Navigation
- ترکیب چند پاسخ API برای یک View در صورت نیاز
- حذف فیلدهای غیرضروری از پاسخ UI
- Route Handler یا Server Action محدود برای نیازهای مرورگر
- Metadata، Sitemap، Robots و Structured Data عمومی

Next.js نباید:

- مستقیم به PostgreSQL وصل شود.
- Balance یا سهم درمانگر را محاسبه کند.
- State Transition مالی را مستقلاً انجام دهد.
- مجوز سمت NestJS را دور بزند.
- DTO و قانون دامنهٔ موازی و متفاوت بسازد.
- یک Generic Catch-all Proxy بدون کنترل ایجاد کند.

### 27.6 سیاست Backend for Frontend

در این پروژه BFF **محدود و هدفمند** است، نه یک Backend دوم.

مسیرهای پیشنهادی:

```text
Browser
  -> Next.js page / Server Action / explicit Route Handler
       -> generated server-only API client
            -> NestJS REST API
                 -> PostgreSQL
```

قواعد:

1. Server Componentهای Next.js برای دریافت داده، از Server-only API Client مستقیماً NestJS را صدا بزنند؛ درخواست نباید ابتدا به Route Handler همان Next.js برود و یک Hop اضافی بسازد.
2. Client Componentها فقط در صورت نیاز تعاملی، Server Action یا Route Handler مشخص و محدود را صدا بزنند.
3. Route Handlerها Endpoint عمومی هستند و باید Auth، CSRF/Origin، Rate Limit، Validation سطح Transport و مدیریت خطای امن داشته باشند.
4. تمام ورودی‌ها در NestJS دوباره Validation شوند؛ اعتماد به Validation لایهٔ Next ممنوع است.
5. Next.js فقط Orchestration و Shape مخصوص View انجام دهد؛ منطق مالی در NestJS باقی بماند.
6. BFF نباید پاسخ خام و بیش‌ازحد NestJS را بدون محدودکردن داده به Browser منتقل کند.
7. برای هر Endpoint BFF باید دلیل مشخصی مانند Session، Same-origin، Aggregation، Upload، Download یا Client-side interaction وجود داشته باشد.
8. ایجاد Proxy عمومی `[...path]` به همهٔ Endpointهای NestJS ممنوع است مگر در Plan به‌صورت مستند و با کنترل امنیتی تأیید شود.

### 27.7 احراز هویت و مجوز

Plan Mode باید بین Session و Token Flow یک طرح دقیق ارائه کند. پیش‌فرض معماری:

- مرورگر فقط Cookie امن، `HttpOnly` و `SameSite` مربوط به Next.js را نگه دارد.
- Next.js Credential یا Token لازم را فقط در Server Context استفاده کند.
- NestJS هر درخواست محافظت‌شده را مستقل Authenticate و Authorize کند.
- نقش مدیر یا منشی در NestJS Guard/Policy بررسی شود؛ پنهان‌کردن دکمه در UI مجوز محسوب نمی‌شود.
- عملیات Mutating از مرورگر محافظت CSRF/Origin داشته باشد.
- Token یا Session Secret در Client Bundle، Log یا Repository قرار نگیرد.
- Refresh، Logout، Expiration و Revocation در Plan روشن شوند.

Claude Code حق ندارد فقط به Middleware یا UI در Next.js برای امنیت پنل تکیه کند.

### 27.8 قرارداد API

- NestJS با Swagger/OpenAPI قرارداد API را تولید کند.
- Client تایپ‌شدهٔ Next.js از OpenAPI تولید شود.
- فایل تولیدشده دستی ویرایش نشود.
- CI بررسی کند تغییر API بدون به‌روزرسانی Client باقی نمانده باشد.
- DTOهای مالی و ورودی‌های Mutation در NestJS تعریف و Validation شوند.
- Package مشترک نباید Decoratorهای Nest یا کد Runtime Backend را به Browser Bundle وارد کند.
- خطاها Code پایدار و پیام فارسی قابل نمایش داشته باشند.
